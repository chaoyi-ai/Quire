# 调研：成熟 macOS 应用的窗口结构，与 Quire 自己的方案

> 2026-09-13。起因：0.6.3–0.9.2 在标题栏 / 侧栏 / 标签栏上反复打补丁（浮板外圈、标题栏带、侧栏材质、系统标签栏、自绘标签栏），
> 每次修一处露出另一处。根因不是某个控件用错，而是**没有先定下窗口的结构模型**——文档、窗口、标签、侧栏各自是什么关系。
> 本文先看别人怎么定的，再定我们的，再把每条规则写成可检查的约束。配套稿：[窗口设计方案（可视化）](https://claude.ai/code/artifact/13fb4103-37ff-4e0c-bea0-64f63719fb9f)。

## 1. 别人怎么做

| 应用 | 窗口 = 什么 | 侧栏 | 标签 | 工具栏 | 备注 |
|---|---|---|---|---|---|
| **Xcode** | 一个工作区（项目） | 左列全高，从工具栏之下开始，自带顶部页签（Navigator） | 编辑器标签**只在编辑器列里**，与侧栏无关 | 整宽一条，左段（导航开关）与侧栏同宽 | 单击文件 = 在当前编辑器里打开，双击 = 新标签 |
| **Nova（Panic）** | 一个工作区 | 左列全高，顶部一排功能页签（Files / Find / Git…） | 标签在编辑区顶部，**单击文件开临时标签（斜体）、再单击别的文件就替换，改动后转正；双击直接固定** | 整宽 | MacStories：像 Mac 的地方是"文件浏览器就像 Finder 一样工作"，不像的地方是"没有 Mac 式标题栏 / 大纲 / 标签" |
| **Obsidian** | 一个 vault | 左侧功能带 + 可折叠侧栏，全高 | 每个编辑窗格自己的标签条，在窗格顶部 | 无系统工具栏 | 侧栏和正文各自独立滚动 |
| **Bear / Ulysses / Notes** | 一个库 | 三栏（侧栏 / 列表 / 正文），全高 | **没有标签**：点列表即切换正文 | 整宽 | 一次只看一篇；要对照就开新窗口 |
| **Typora / iA Writer** | 一篇文档（Typora 有文件树） | 可选侧栏（文件树 / 大纲） | 没有标签 | 极简 | 点侧栏文件 = 就地替换当前文档 |
| **Finder / Mail（macOS 26）** | 一个位置 | 系统浮板侧栏（内缩、玻璃） | 系统标签栏 | 整宽 | 26 的浮板被广泛批评（"双层边框"），27 改回贴边 |

三条共识：
1. **标签属于正文列，侧栏属于左列，两者互不覆盖。** 没有任何一个成熟应用把标签条横跨在侧栏之上。
2. **侧栏从工具栏之下开始**（Xcode / Nova / Obsidian）或与标题栏并列（系统浮板）；两种都成立，但**不能同时**又顶穿标题栏又被标签条压住。
3. **单击侧栏文件 = 在当前位置打开，不产生新窗口。** 要么无标签就地替换（Bear / Typora），要么临时标签（Nova / VS Code / Xcode）。

Apple 26 的官方口径（WWDC25-356）：铬"浮在内容之上"、去掉自定义背景、用布局和分组表达层级、滚动边缘用模糊代替硬分隔线。这套是给系统材质设计的；Quire 自己按主题铺色，铬不能用系统材质（0.6.3–0.9.1 的教训），所以只取它的**结构**观点：铬是一层、内容是一层，边界清楚。

## 2. Quire 的模型（定死）

**一个窗口 = 一个工作区（根目录）。文档是标签，不是窗口。**

- 侧栏是工作区的，不是文档的：一个窗口一个侧栏，切换标签它不动。
- 单击侧栏文件：在当前标签打开（Nova 的临时标签：标题斜体；再单击别的文件就替换；一旦编辑就转正）。双击 / ⌘单击：固定成新标签。侧栏的选中永远等于当前标签（避免 Nova 那个"高亮的不是正在看的"的困惑）。
- 新窗口只有两种来源：文件 → 新建窗口，或把标签拖出去（长期）。打开另一个根目录 = 另一个窗口。
- 每个文档仍是独立 `NSDocument`（脏标记、关闭询问、自动存储、版本都照旧）；窗口控制器同一时刻只挂在当前标签的文档上，切换标签时换挂。

## 3. 布局规则（可检查）

```
┌─ 工具栏行 38 pt（标签就在这一行）──────────────────────────────────────────┐  铬色
│ [●●●] [⊟] │ README │ DESIGN ╭THEMES╮ +        [阅读|编辑|双栏|混合]  ·  Aa ◐ 🎨 │
├─ 侧栏 240 ┼──────────────────────────────────────────────────────────────────┤
│ 根目录 ▾   │                                                                  │
│ 筛选框     │                         正文列                                    │  正文 = 主题背景
│ Files 树   │                                                                  │
└───────────┴──────────────────────────────────────────────────────────────────┘
```

1. **两种颜色**：铬（工具栏行 + 侧栏）= `ChromeColors.elevated(主题背景)`；正文 = 主题背景。标题栏透明，不用系统材质。
2. **每样东西只属于一列**：侧栏从工具栏行之下开始、到窗口底；标签在工具栏行里、侧栏列右侧；工具栏左段与侧栏同宽。侧栏折叠时左段只剩侧栏钮。
3. **颜色表示层，状态是同一层上朝墨走一步**（0.10.2）：正文色只给正文；铬上的选中 / 悬停 / 分隔线 / 文字都是铬色朝白（深色）/ 黑（浅色）走一档（`ChromeColors.ink` + `ChromeStep`），方向与系统分段控件、侧栏选中一致。选中标签 = 和模式分段控件选中段同高同色的底板，整条只有这一块；悬停不加底。详见 DESIGN.md §8.1。
4. **正文从工具栏行之下开始**，永远不滑到铬底下。
5. **字数胶囊**贴正文列右下角。
6. 这几条之外不再有任何系统绘制的铬：没有系统标签组（`tabbingMode = .disallowed`）、没有系统侧栏浮板、没有材质。

> 0.10.0–0.10.1 是 52 pt 工具栏行 + 30 pt 标签条两行（选中标签 = 正文色 + 2 pt accent 顶线，贴着正文）。0.10.2 合成一行时一度保留了"选中 = 正文色"，但标签不再贴着正文，正文色块浮在铬上，深色主题里像个洞——规则 3 就是从这次教训来的（调研、候选方案与真实截图盲测见 0.10.2 的提交说明）。

## 4. 实施计划（M9「工作区窗口」，替换 0.9.2 的 TabGroups）——0.10.0 已完成

- [x] `WorkspaceWindowController`：持有 `[DocumentTab]`（NSDocument + DocumentSession + 阅读 / 编辑窗格 + 模式 + 滚动位置）；`current` 切换时换挂 `document`、换 contentSplit 的子视图、更新标题 / 脏标记 / 侧栏选中；关闭标签走 `canClose(withDelegate:)`；关窗口逐个询问未存储的文档，都同意才开始关，取消时所有标签都留着（询问只走 `windowShouldClose`，文档层 `shouldCloseWindowController` 放行；0.10.2 之前两边都问，同一份文档重入 `canClose` 会死锁）
- [x] `NSDocumentController` 子类：打开文件时若 key 窗口是工作区且文件在其根内 → 作为标签打开（临时 / 固定按来源），否则新窗口；`makeWindowControllers` 不再每文档一窗
- [x] 标签条 `TabStripView` 移到正文列顶部（paneHost 之内，不再是标题栏附件）；临时标签（斜体）状态
- [x] 工具栏左段与侧栏同宽：自定义 spacer item 的宽度跟随侧栏宽度（折叠时 0）；标题 / 模式段在右段居中
- [x] 侧栏从工具栏行之下开始（不再全高）；铬带只盖工具栏行
- [x] 沉浸模式：隐藏标签条与侧栏，退出恢复
- [x] 状态恢复：按窗口恢复根目录 + 标签列表 + 当前标签 + 模式 + 窗口位置（自己存 `WorkspaceState`，窗口 `isRestorable = false`；未命名文档不恢复）
- [x] 删除 `TabGroups`（0.9.2 的过渡方案）；DESIGN.md ADR-18 改写为本文的模型
- [x] 验证矩阵：单标签 / 多标签、侧栏折叠、切换主题、双栏、沉浸、关闭有改动的标签、关窗口、状态恢复——每项截图 + 像素测量（工具栏行 / 标签条 / 侧栏三者同色、正文不被遮）。更正：这轮的「关窗口」没走到 `performClose`，所以没发现它会卡死；现在由 QuireAppTests 的关闭用例覆盖
